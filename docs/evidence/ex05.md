## Setting and prediction

**Setting:** the supplied simulation. `site.lab.example` should reach a new
Railway deployment. The Railway-provided URL already returns the current page
and database content. Cloudflare is authoritative for `lab.example`, and the
record is **DNS only**, so visitors connect straight to the origin with no
Cloudflare proxy in between.

**Failed check:** `dig site.lab.example A` followed by
`curl -Iv https://site.lab.example/`.

**Prediction (what should happen):**

1. `dig` should show `site.lab.example` as a **CNAME** to
   `current-app.up.railway.app`, followed by Railway's address. It should not
   show an Azure IP.
2. `curl` should connect to a Railway address, and the TLS handshake should
   present a certificate whose name covers `site.lab.example`.
3. The HTTP response should be a `2xx`/`3xx` status from the app, and the page
   should show the same content as the Railway-provided URL.

## Failed check and evidence

**Command:** `dig site.lab.example A +noall +answer`, then
`curl -Iv https://site.lab.example/`
**Date:** supplied with the Ex05 handout; interpreted on 2026-10-12.
**Result (simulated, quoted from the handout):**

```text

$ curl -Iv https://site.lab.example/

* SSL: certificate subject name does not match target host name 'site.lab.example'
```

The zone before repair (simulated) still held the old Azure record:

```text
site.lab.example.  300  IN  A  198.51.100.24
```

Every part of this differs from the prediction:

| Check | Predicted | Actual (simulated) |
|---|---|---|
| DNS answer | CNAME → `current-app.up.railway.app` | A → `198.51.100.24` (old Azure VM) |
| Connected address | a Railway address | `198.51.100.24` |
| Certificate name | covers `site.lab.example` | `CN=old-vm.lab.example` |
| HTTP result | 2xx/3xx from the app | none, because curl stopped at TLS with error 60 |

## Diagnosis

The problem started with DNS, not the certificate. In the supplied `dig`
output, the domain still had an A record pointing to `198.51.100.24`, which is
the old Azure VM's IP. So the cutover to Railway never happened in DNS.
Because of that, curl connected to the old VM (the
`Connected to … (198.51.100.24)` line shows this). The old VM sent its own
certificate, `CN=old-vm.lab.example`. That didn't match `site.lab.example`,
so curl stopped with error 60 before it sent any HTTP request. The
certificate error was a symptom. The real cause was stale DNS sending me to
the wrong server.

**What remains uncertain:**

- Whether Railway has already issued a certificate for `site.lab.example`. The
  handout says the ownership TXT record verified, but a verified domain can
  still be waiting for its certificate. That can only be tested once traffic
  actually reaches Railway.
- How long resolvers will keep serving the old answer. The TTL is 300 s, so
  caches should expire within about 5 minutes of the change. Some resolvers
  may still give mixed answers for a short time.
- Whether the app and database respond on the custom hostname. A correct DNS
  answer alone doesn't prove that HTTPS or the page content work.

## Repair and repeated check

**Proposed repair (written before looking at the follow-up):**

1. In Cloudflare, **delete** the A record `site.lab.example → 198.51.100.24`.
   It has to be removed rather than kept alongside the new record, because a
   name with a CNAME can't have any other record type.
2. **Add** a CNAME record: `site` → `current-app.up.railway.app`, **DNS only**
   (gray cloud), so Railway can complete its own certificate check and serve
   TLS itself.
3. Wait at least one TTL (300 s). Then repeat **the same two commands** and
   confirm all three predictions: the DNS answer, the connected address with a
   matching certificate, and an HTTP status from the app. Finally, load the
   page and compare its content with the Railway-provided URL.

This repair only touches DNS. The old VM's certificate shouldn't be "fixed",
because the goal is to stop sending visitors to that server, not to make it
look valid for this name.

**Repeated check (simulated follow-up):** the handout says a lab operator made
one record change and waited for the DNS answer to update. I interpreted the
supplied output rather than running it.

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

| Check | Before (simulated) | After (simulated) |
|---|---|---|
| DNS answer | A → `198.51.100.24` | CNAME → `current-app.up.railway.app.` → A `203.0.113.44` |
| Connected address | `198.51.100.24` (old Azure VM) | `203.0.113.44` (Railway) |
| Certificate name | `CN=old-vm.lab.example`, which doesn't match | `CN=site.lab.example`, verified ok |
| HTTP result | none (curl error 60 at TLS) | `HTTP/2 200` |

**What changed and what it shows:** it took one DNS change. The lab operator
replaced the A record with a CNAME to `current-app.up.railway.app`, which
matches the repair I proposed. The A record had to be removed, because a name
can't have a CNAME alongside other records. After that, everything lined up.
DNS returned the CNAME and then Railway's IP, `203.0.113.44`. curl connected
to that IP, the certificate was `CN=site.lab.example` and verified, and the
result was `HTTP/2 200`. The certificate was never touched. Once traffic
reached the right server, the right certificate was already there. One limit:
a 200 from `curl -I` only proves the server answered. It doesn't prove the
page is showing the current database content.

**Does the follow-up support my diagnosis?** Yes, the repeated check supports
my first diagnosis. After one DNS change, swapping the stale A record for a
CNAME to Railway, every check that had failed now passed, even though the
certificate was never changed. That shows the TLS error was only a symptom of
reaching the wrong server, so I didn't need to revise anything.

## What you learned

I'd skip DNS and test the destination directly, either with
`curl -Iv https://current-app.up.railway.app/` or with
`curl --resolve site.lab.example:443:<Railway IP> https://site.lab.example/`.
If that works but the normal check fails, it's a DNS problem. If I still get a
certificate error while hitting Railway directly, it's a TLS problem. If the
certificate is fine but I get an error status or the wrong page content, it's
an app problem. Either way, the first thing I check is the `Connected to (IP)`
line, because it tells me which server I actually reached.

**If the failure remained after the DNS change**, I'd check these next:

- Query the authoritative server directly (`dig @<cloudflare-ns> site.lab.example`)
  and also public resolvers (`@1.1.1.1`, `@8.8.8.8`), to see whether the old
  answer is still cached.
- Make sure the record is gray-cloud (DNS only).
- Check the Railway dashboard to see whether the custom domain's certificate
  shows as issued.

What I took from this: an HTTPS error isn't necessarily a certificate problem.
The first question is **which server did I actually connect to**, and the
`Connected to … (IP)` line answers that.
