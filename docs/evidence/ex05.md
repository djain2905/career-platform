## Setting and prediction

**Setting:** the supplied simulation. `site.lab.example` should reach a new
Railway deployment. The Railway-provided URL already returns the current page
and database content. Cloudflare is authoritative for `lab.example`, and the
record is **DNS only**, so visitors connect straight to the origin with no
Cloudflare proxy in between.

**Failed check:** `dig site.lab.example A` followed by
`curl -Iv https://site.lab.example/`.

**Prediction (what should happen):**

1. `dig` should show `site.lab.example` as a **CNAME** to
   `current-app.up.railway.app`, followed by Railway's address. It should not
   show an Azure IP.
2. `curl` should connect to a Railway address, and the TLS handshake should
   present a certificate whose name covers `site.lab.example`.
3. The HTTP response should be a `2xx`/`3xx` status from the app, and the page
   should show the same content as the Railway-provided URL.

## Diagnosis

**DNS → destination.** DNS answers first, and it answers with the **old Azure
A record** (`198.51.100.24`) instead of a CNAME to Railway. Nothing is wrong
with the lookup itself: the resolver got a valid answer from Cloudflare, the
authoritative server. The zone simply still holds the old record, so the
cutover to Railway never happened in DNS.

**TLS → certificate.** Because DNS gave the old address, curl connected to
`198.51.100.24`, the old VM, not Railway. That machine presented its own
certificate, `CN=old-vm.lab.example`, which doesn't cover `site.lab.example`.
So curl refused the connection (error 60) before any HTTP request was sent.

**Which observation supports this.** The deciding line is
`Connected to site.lab.example (198.51.100.24)`. It shows that the TLS error
happened on the *wrong server*, and it matches the stale A record in the `dig`
output. The certificate mismatch is a **symptom** of the DNS fault, not a
separate certificate problem. Railway's certificate never came into it,
because the request never reached Railway.

**What the evidence supports:** the root cause is a stale DNS record. The
first fault in the chain is DNS, and the TLS failure follows from it.

**What remains uncertain:**

- Whether Railway has already issued a certificate for `site.lab.example`. The
  handout says the ownership TXT record verified, but a verified domain can
  still be waiting for its certificate. That can only be tested once traffic
  actually reaches Railway.
- How long resolvers will keep serving the old answer. The TTL is 300 s, so
  caches should expire within about 5 minutes of the change. Some resolvers
  may still give mixed answers for a short time.
- Whether the app and database respond on the custom hostname. A correct DNS
  answer alone doesn't prove that HTTPS or the page content work.

   name with a CNAME can't have any other record type.
2. **Add** a CNAME record: `site` → `current-app.up.railway.app`, **DNS only**

## What you learned

**One check that separates DNS from TLS or application problems:** skip DNS and
aim the request directly at Railway. For example:

```text
curl -Iv https://current-app.up.railway.app/
curl -Iv --resolve site.lab.example:443:<Railway IP> https://site.lab.example/
```

The first command tests the app on Railway's own hostname, with no custom DNS
involved. The second sends the real hostname (so the TLS name check is the
same) to a chosen IP, which bypasses DNS entirely. Reading the results:

- Both succeed while the normal check fails → the problem is **DNS**.
- `--resolve` fails with a certificate mismatch → the problem is **TLS** on
  Railway (no certificate issued yet for the custom name).
- TLS succeeds but the status is 4xx/5xx or the page lacks the database
  content → the problem is the **application**.

`openssl s_client -connect <ip>:443 -servername site.lab.example` gives the
same certificate answer without HTTP.

**If the failure remained after the DNS change**, I'd check these next:

- Query the authoritative server directly (`dig @<cloudflare-ns> site.lab.example`)
  and also public resolvers (`@1.1.1.1`, `@8.8.8.8`), to see whether the old
  answer is still cached.
- Make sure the record is gray-cloud (DNS only).
- Check the Railway dashboard to see whether the custom domain's certificate
  shows as issued.

What I took from this: an HTTPS error isn't necessarily a certificate problem.
The first question is **which server did I actually connect to**, and the
`Connected to … (IP)` line answers that.
